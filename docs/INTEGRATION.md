# React 应用接入与抽离边界

本仓库交付 neuro 的标准组件实现。内部应用目前采用本地 `file:` 依赖，安装构建产物，不复制组件源码；应用的业务接口与流程仍由各自仓库维护。

## 本地依赖（当前方式）

设计系统检出在 `C:\Users\Public\nas_home\NeuroDesign`，两个应用位于 `C:\Users\Public\nas_home\AI\GameEditor\Neuro\Gateway` 和 `Loom`。它们的 `apps/desktop/package.json` 引用：

```json
"@neuro/ui": "file:../../../../../../NeuroDesign/packages/react/neuro-ui"
```

先在设计系统根目录使用 npm 11 安装开发依赖。检出目录改名后也应运行 `npx --yes npm@11 install --ignore-scripts --prefer-offline --no-audit --no-fund`，由 npm 修复根 `node_modules` 的 workspace 链接；`@neuro/ui` 和 `@neuro/preview` 应分别解析到当前目录的 `packages/react/neuro-ui` 和 `apps/react/neuro-preview`，不能仍指向旧检出目录。

首次接入或本地 `file:` 路径变化时，先在各应用的 `apps/desktop` 目录执行：

```powershell
npx --yes npm@11 install --install-links --ignore-scripts --prefer-offline --no-audit --no-fund @neuro/ui@file:../../../../../../NeuroDesign/packages/react/neuro-ui
```

这一步通过 npm 更新 lockfile 和实际安装地址；应核对 manifest 的依赖、lockfile 根依赖及 `packages["node_modules/@neuro/ui"].resolved` 一致，并保留其他包的锁定版本。仅路径变化时包元数据可能相同，不能用 `ui:sync` 代替安装和锁文件更新。随后日常同步运行：

```powershell
npx --yes npm@11 run ui:sync
npm run typecheck
```

应用的 `ui:sync` 脚本显式使用 `node ../../../../../../NeuroDesign/scripts/sync-consumer.mjs --package @neuro/ui`，只构建选定的 React 主题库及必要共享依赖，不构建其他主题、预览或原生组件。同步比较全部分发文件与包元数据，按需刷新本地包，校验 React / React DOM 唯一及 Radix 焦点/弹层上下文共享。`.npmrc` 固定 `install-links=true`，消费已构建副本而非链接开发仓库的 React；不要同时运行其他 npm 安装或构建。

组件源码改动只同步构建产物，不卸载或重装应用的其他依赖。包版本、依赖或导出元数据变化时由 npm 安装；如果 npm 仍保留同版本旧元数据，同步会明确失败，必须递增包版本后重新安装，不能把依赖不匹配伪装成已同步。

普通 `npm install` / `npm update` 可能把同版本的 `file:` 包视为最新，即使源目录的 dist 已变化；更新库后必须执行 `ui:sync`。这不是复制或维护组件源码，源码始终只有本仓库一份。

另一台机器或 CI 需同时检出、构建本仓库，并保持依赖的相对目录关系，再在应用执行 `npm ci`。预先同步本地包的更新应随应用 lockfile 一起纳入交付。独立运行的成品应用不需要设计系统源目录；已经构建的应用仍需重新构建、分发才会包含新控件。

## 可选的成品包分发

1. 在本仓库执行 `npm ci`、`npm run check`、`npm run pack:ui`。
2. 在目标应用安装生成的 `neuro-ui-<version>.tgz`。React / React DOM 使用应用自己的 React 19 实例。
3. 表现层入口引入 `@neuro/ui/styles.css` 并放置 `NeuroProvider`，按需添加 `ToastProvider`。
4. 将通用控件改为包入口引用；业务值、API 调用、权限和持久化仍由应用传入。
5. 同一批改动完成实际引用方的类型检查、相关行为验证和构建。已编译的桌面应用需重新分发。

内部统一跟进当前接口，不维护旧接口。包的版本用于记录交付，不代表承诺长期兼容或同时支持多套接口。

Radix 组件使用经本库测试的一组精确版本，避免宿主已有依赖将 Dialog 与 Popover 分别解析到不共享焦点栈的版本。不要只在宿主覆写某个 Radix 内部包来消除重复项；应验证库内组合控件的真实焦点与嵌套交互。宿主原有版本范围可能允许 npm 同时去重统一旧控件的 Radix 版本，因此更新后也要复核仍直接引用 Radix 的应用控件。

普通 tarball 安装能让 peer dependencies 使用应用的 React，避免开发仓库的 React 实例随本地符号链接被误加载。跨仓库开发如使用符号链接，必须验证 React 实例唯一，并配置构建器跟踪包的构建输出；不能仅执行一次链接就认为所有已经构建的应用会自动更新。

## 通用组件对应关系

| 现有能力 | 标准实现入口 | 应用保留的部分 |
|---|---|---|
| 提示气泡包装 | `ActionTooltip` | 实际标签、权限和触发按钮 |
| 通知渲染 | `ToastProvider` + `useToast` 或受控 `ToastViewport` | 发布入口、判断真实操作结果，错误持久化与恢复 |
| 确认弹窗 | `ConfirmDialog` / `Dialog` | 任务执行、确认请求的业务排队、应用退出语义 |
| 按钮和图标操作 | `Button` / `IconButton` | 操作回调、可用性和权限 |
| 按钮式导航 | `ButtonLink` | URL 安全、路由策略、原生链接的 target/rel；不可用时显示禁用 Button |
| 表单与设置项 | `Field`、输入/选择组件 | 字段模型、业务校验、保存和加载 |
| 弹出式单选 | `PopupSelect` | 业务 ID 的编码、过滤与标签；原生分组选择仍可用 `Select` |
| 可搜索多选下拉 | `MultiSelect` | 选项数据、可用性、数量上限、简短摘要与不支持原因 |
| 搜索联想 | `SearchCombobox` | 查询索引、匹配、结果上限、路由/定位，以及原生子视图的显示策略 |
| 复制操作 | `CopyButton` | 权限、获取真实内容、宿主剪贴板写入及敏感值寿命 |
| 可组合页签 | `TabsRoot`、`TabList`、`Tab`、`TabPanel` | 工作区身份、数据筛选、保留面板状态及工具栏位置 |
| 折叠分区 | `Disclosure` | 受控展开规则、是否卸载内容、业务草稿 |
| 选择列表/表格 | `DataTable` + `SelectionBar` | 数据、稳定标识、排序/筛选规则、批量操作 |
| 应用壳层 | `AppShell` 等可选模板 | 导航信息架构、路由、宿主窗口与业务页面 |

Gateway 的 tooltip 包装已是 React + Radix 的组合，这种交互基础被保留在库内，而项目名称和业务文案不进入库。Loom 的反馈模块同时包含业务类型与 UI，不应整份搬进组件包；只替换渲染和通用交互部分，保留业务归属。

## 当前接入范围

- Gateway：由原有 `UiThemeProvider` 传入已解析的深浅色；迁入四处弹出式单选、账号操作提示、通知展示和凭据池删除确认。ID 编码、权限、提交、通知发布仍由 Gateway 管理。
- Gateway 的账号删除确认与失效号清理也使用标准弹窗、按钮和复选框。归档成功后移除、显式选择、128 项上限、锁定/执行中禁用及部分失败回执仍属于应用。
- Gateway 的账户计费倍率和 Key 账单通过业务容器使用标准弹窗及基础表单控件；金额校验、留空重置/零值、结果不确定时重读、账单快照、权限和请求取消仍由应用管理。
- Gateway 的存储/归档连接编辑与生命周期确认也使用标准弹窗；认证补丁、连接身份隔离、HTTP 风险确认和删除/归档规则仍由应用负责。原入口禁用后返回同一卡片可用位置的逻辑通过 `resolveReturnFocus` 由应用解析，库只管理通用焦点生命周期。
- Gateway 的 API Key 创建/编辑、额度输入、权益组多选、一次性结果、复制、列表及启停/轮转/删除确认已使用标准组件。真实密钥读取、明文寿命、额度单位/有效性、128 组上限、不可用项取消、异步锁定和失败保留草稿仍由应用管理；没有将管理 API 或业务 hook 移入库。
- Gateway 的设置导航、搜索联想、外观/连接/诊断/管理安全表单及密钥弹窗已使用标准组件。设置 catalog、跨分类定位、偏好存储、密钥明文寿命、导出和原生子视图仍在应用；标准控件响应原有字体与字号偏好。
- Gateway 的登录、初始化、错误重试和敏感授权确认也使用标准面板、字段、操作、反馈及弹窗。会话协议、密钥归一化、失败草稿和关闭清空留在应用；busy 关闭保护、初焦与返回焦点由标准实现负责。
- Gateway 的共享壳层导航与普通操作使用 NavigationItem、IconButton，保留的 App 入口使用标准启停操作、徽标、面板和反馈。路由、侧栏布局与折叠焦点接线仍在应用；原生 bridge、窗口指令、拖动和快捷键监听不进入库。旧导航/窗口控件皮肤已退出，窄屏双行标题栏避免普通操作被固定窗口按钮遮挡。
- Gateway 保留的旧桌面配置、API 测试、日志、启动台、模型和状态页面使用标准字段、单选/下拉、操作、面板、状态和空态，模型目录使用 DataTable。配置/状态 hook、模板、导入导出、诊断脱敏、原生 IPC、HTTP 解析与轮询不进入库；已有业务复制回调自己处理结果时只替换 Button，不叠加会误判成功的复制反馈。
- Gateway 的供应商目录使用标准分类单选、操作、五个保留 DOM 的页签、字段、开关、反馈及 Dialog；共享 Qwen 目标字段和卡片客户端选择也已统一。模板、后台刷新草稿保护、32 个关联上限、测试策略、号池驱动白名单、目标变化时清除暂存秘密和创建序列化仍属于应用。已取消勾选的手工目标保留在本次编辑候选中，不因关联变化卸载控件；候选不额外持久化。
- Gateway 的账号材料编辑、模型双栏、密钥显示操作、协议折叠、Bedrock/产品会话字段、可见文件入口与 Qwen 目标设置使用标准组件。账号草稿控制器和业务字段按职责分离但不进入库；目录/秘密请求、权限撤销、材料受众、解析与独立秘密补丁仍由 Gateway 管理。普通表单异步读取允许取消并拒绝迟到结果，不把业务 `locked` 或读取状态错误地映射成禁止关闭。

## 不应搬进组件包

- 供应商、账户、路由、设备、插件、工作流等领域模型和页面控制器。
- Tauri API、Rust IPC、网络客户端、鉴权或任务生命周期。
- 依赖某个应用上下文才能工作的模块级单例、业务全局事件总线。
- 仅为了保留旧调用形式而增加的接口别名或兼容适配层。

库允许界面自身的短暂状态，例如输入草稿、展开、焦点与通知；不能把应用执行任务藏在这些状态里。

## 固定主题与 CSS

库只在 Provider 内应用基础排版与固定变量，组件类使用 `n-` 前缀，弹层在所属 Provider 的 portal 中渲染。应用使用 `inheritTypography` 继承自己的用户字体与字号设置。标准控件不再使用旧视觉类；应用样式只负责产品布局、领域可视化和必要的宿主目标，避免全局选择器覆盖标准表现。

项目独有内容仍可编写自己的样式，但遵循声明层，不再复制一份基础按钮、弹窗、选择器。不要为了维持历史差异保留两套同名标准控件。

## 非 React 项目

优先使用主题已正式提供的对应技术栈实现；Windows 原生组件未来位于 `packages/windows-native`，使用 Cargo 独立依赖、构建与验证，不通过 `ui:sync` 或 React 包接入。目前 neuro-mini 仍只有声明层，没有可安装的原生 crate。

未正式提供的技术栈，可结合声明与标准预览自行实现，由下游维护；不把它变成 `@neuro/ui` 的适配分支。完整的主题/技术栈边界见 [ARCHITECTURE.md](ARCHITECTURE.md)。
